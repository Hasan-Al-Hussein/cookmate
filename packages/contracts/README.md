# Shared contract v2

Canonical source: `schema/contract.schema.mjs`. Run `npm run contracts:generate` after an approved edit, then `npm run contracts:check`. Generated TypeScript, validators, JSON schema and size/fingerprint manifest are under `src/generated`. Never edit generated output or compile model-provided schemas.

Import types, generated shape validators and pure helpers from `@cookmate/contracts`. Build/gateway schema setup may import `@cookmate/contracts/schema`; mobile code must use generated validators and never import the schema compiler entry. The generated package has no UI, SQL, filesystem, provider or secret dependency. Pure domain consumes it; repositories and native/provider adapters sit outside it. The gateway has no phone-state write authority.

## New requests and first acceptance

1. Bound input bytes at transport (assistant JSON: 128 KiB); authenticate on the gateway before provider work. Derive client scope from the credential registry, never a request `clientId`.
2. Apply strict shape validation. Fastify must reuse `strictAjvOptions`: no coercion, inserted defaults or unknown-field removal. All nested objects reject unsupported fields.
3. Use `checkAssistantRequest`/`checkAssistantResponse`/`checkLocalCommand` for intrinsic dates, catalogue compatibility, IDs, relative-date binding and source ownership. Request checks include `checkMemoryRequest`; response checks also bound expanded bytes. `CatalogueBoundary` requires `identity`, `recipeIds`, and `hasSource(reference)`; Data implements the last lookup with **recipe + section + position/annotation ID**, never global position alone. Citation existence does not prove every prose claim is grounded.
4. For a **first acceptance**, use `checkMemoryResponseForRequest(response, frozenRequest)` for correlation, frozen bases, review bijection, source membership, exact quotes and backward relations. Then compare current `ActiveResponseContext` with `isResponseCurrent`, and check retained originals, generation, current intent/authority, recipe evidence, target/scope/preference revisions and confirmation against the phone repository. A schema-valid model proposal is not authorization. Exact retries follow the replay order below before these checks.

`validate*` exports are deliberately shape-only. `isActualLocalDate` is the Gregorian primitive; the LocalDate schema restricts product dates to 1900-01-01 through 2100-12-31. UTC audit timestamps are a separate representation. Persist the interpretation date/timezone/offset for relative dates and compare again at commitment. Committed calendar dates never shift on timezone changes.

## Source memory and model boundary

`context.memory` replaces `context.facts`; old payloads reject. Each item retains its complete USER quote (at most 4,000 Unicode code points), app-assigned ID/revision, original `sourceSequence`, `sourceDateContext`, immutable `preferenceRevisionAtSource` and app-derived `preferenceLinks`. USER history carries the same original provenance while retaining `messageId`/`text`. Assistant history carries app sequence only. The current message uses `messageId`/`text` plus source provenance, with empty links at begin. Frozen retries never rebuild that source using newer state. Sequence is a nonnegative safe integer, verified against the retained generation by Data; reading a proposed next sequence does not reserve it.

The packet includes at most 32 items, 7 pending/reconsidered sources, and 8 unique review targets including the current USER source. Every target has one full supplied USER record. Coverage counts include the proposed current source in both pending totals, verified when begin appends it. Retained = supplied + omitted; supplied counts match arrays. Reconsidered targets need not all be pending. Counts and model scopes are relevance hints, never proof of semantic completeness. Full projection/backlog retention, applicability selection and required relation groups belong to Data. The original date and preference state must come from one verified app snapshot.

With no working boundary, scoped pending and total pending counts must agree; a smaller claimed scoped count cannot silently exclude the backlog. Withdrawals attached to a source must have a global `removedRevision` strictly after that source's global `preferenceRevisionAtSource`. The saved **row** revision is not part of this comparison. Live links must match the frozen snapshot's ID/version/type/value, and removed versions cannot simultaneously be current.

Normal answer, clarification and proposal responses require `MemoryUpdate`; errors forbid it. `ModelMemoryUpdate` is a distinct strict quote-free schema: the model emits IDs/dispositions/kind/scope/relations, never source quotes, IDs to persist, preference links or reset authority. Gateway copies each exact entire quote from the already disclosed frozen USER source. Data independently compares with its retained original, with no trimming or Unicode normalization. Every declared target is reviewed exactly once. Each `retain` has exactly one entry; `non_memory` and `unresolved` have none. Unresolved evidence permits only clarification and remains pending. No extra summary/model call is introduced.

Existing items use resolved memory targets. Update proposals may target selected memory with exact revision or another retained source in that batch. Every edge points to an earlier source sequence, which rejects self-links, forward links and cycles. Data allocates identities and resolves source links atomically. `supersedes` preserves both complete quotes: “Tuesday instead” does not remove the peanut clause from “No peanuts; Monday”. Quoted text is untrusted evidence, never instructions to the application or saved-preference authority.

Each expanded request and response independently must fit 128 KiB of UTF-8 JSON. `assistantJsonByteLength` measures the full serialized body without a platform dependency. Per-quote/code-point caps do not replace the byte cap. Preference links have no separate count cap and are never truncated. Entry/byte/token overflow or undisclosed potentially applicable pending evidence yields Data's typed local narrowing result (`entry_limit`, `byte_limit`, `token_limit`, `pending_evidence`) with counts and explicit recovery controls. `MemoryCoverage` represents local narrowing too, but `checkMemoryRequest` rejects `selectionStatus:'narrowing_required'` as a sendable request. The coordinator returns local narrowing before begin/send; no partial packet, dependent proposal or hidden repeated provider loop may proceed.

## Working scope and preferences

`WorkingContextSelection` is app-owned: nullable `afterSequence` and at most 32 unique `carryMemoryIds`. An explicit guarded `setWorkingContext` port belongs to Data, never to AI capabilities. The user can carry complete established relation groups, or start fresh with no carry and a new USER brief. Data expands chosen roots through the complete undirected relation group (ancestors, branches and corrections) before storing the **expanded** carry IDs. Every carried old source's memory ID is individually present in the stored/wire array; roots alone are not the stored representation. The boundary excludes older history, memory, pending reviews, unresolved intents and implicit references across **all** outbound channels unless explicitly carried/reintroduced. Fresh context preserves the local transcript/projection; excluded pending sources no longer block that task. Data validates retained range, group closure, same-generation carry, reference-set origins and all state-dependent selection. The pure helper can check only the disclosed packet. Scope changes atomically advance semantic context revision and invalidate uncommitted authority; receipts and committed effects survive.

`PreferenceSnapshot` alone governs saved preferences. Its required nullable `lastRemovalRevision` records the last actual withdrawal's post-commit global revision. `sourcePredatesPreferenceRemoval` uses strictly `<`; equality allows a new explicit temporary constraint. Empty clear/nonexistent remove must not advance the watermark. Source links contain source ID, actual saved row ID/type/value/version and nullable withdrawal revision; internal `saveOperationId` never appears on wire. Row versions and global revisions are distinct domains. Successful app-authorized save plus receipt creates the link, including no-op duplicate saves linked to the **existing actual row/version**. Replacement withdraws the old version; re-add cannot revive a withdrawn link merely by text equality. Conversation clear removes derived links but retains preferences/receipts; receipt-first command replay cannot recreate cleared links. Removing “Remember Italian” must preserve the separate “no peanuts tonight” clause in a mixed full quote. Ambiguous temporary interpretation requires clarification.

## Immutable acceptance and replay

`acceptanceFingerprintInput` validates and canonically serializes the complete `{normalizationVersion:1, frozenRequest, normalizedResponse, envelope}`. The required envelope contains `assistantMessageId` and `expectedIntentRevision`. Hash its exact UTF-8 output with SHA-256 in the platform adapter. It sorts object keys, preserves all array order/exact strings, rejects unknown fields/non-JSON values, and never projects a hand-selected subset. Errors cannot form an accepted result. This helper deliberately performs no first-acceptance correlation or current-state check; changing a valid normalized field must produce a different fingerprint for conflict detection. It is independent of command fingerprinting.

Load the acceptance record by the persisted stable intent key **before request-ID correlation, stale revision/day/connection checks, and transaction-wrapper current-runtime checks**. Normalize using the original frozen request/envelope, not today's preferences or selection. Exact replay returns the stored immutable historical acknowledgement and assigned IDs without writes. Changed normalized input conflicts. Mobile retains the same envelope after a lost acknowledgement. Historical acknowledgement never renews action availability, cancelled authority or old guards; reading today's mutable intent is not that acknowledgement.

For first acceptance, request base context `c` was verified at begin; append persisted `c+1`. Check actual context against that post-send value while the sidecar base still equals request `c`; compare actual/frozen projection as well. Persist reply/references, source evidence/relations, reviews, revisions, phase, IDs and fingerprint/immutable acknowledgement in one transaction. Failure rolls back all. Never accept an answer while dropping its invalid sidecar. Conversation clear removes acceptance records and old-generation updates reject; receipts cannot revive deleted replies. App-owned `not_executed` status and receipt-only outcomes remain consumer responsibilities.

## Commands, results and retry

Only `saveRecipe`, `addPlan`, and `savePreference` are model proposals. The app creates intent/operation/occurrence identities and frozen slots. Structured commands include edit/remove/move/clear but are not provider capabilities. `origin` is optional, so direct UI commands do not depend on a conversation. Receipts contain no transcript text and must survive clearing conversation.

Call `commandFingerprintInput` on the frozen command and hash the result with SHA-256 through the platform adapter. It projects explicit contract fields and ignores an existing fingerprint. Recompute and verify the fingerprint before receipt lookup; the hash is an equality guard, not permission or authentication. `matchOperationReceipt` returns existing/conflict/missing only after that verification. Record the mutation and receipt in the same transaction.

`addPlan` targets an empty placement. Occupied add becomes `replacePlanRecipe`, retaining B's ID/selection under B and shopping-scope guards. `editPlan` atomically carries recipe, date and meal, requires occurrence **and shopping-scope** revisions, targets an empty placement or the same occurrence, and cannot replace another occupant. `movePlanReplacing` requires A, B and shopping-scope revisions; atomically remove B and move A, preserving A's ID/current inclusion. Never inherit B's selection. Repository checks for actual placement/identity and confirmation are mandatory; types cannot enforce current database truth.

Freeze all requested action slots before dispatch. `summarizeActionResults(result, frozenBatch)` validates unique slots/operations and matches each result with the frozen intent/operation/fingerprint. It returns `invalid` for inconsistent batches, and preserves partial/uncertain outcomes. `uncertain` requires receipt reconciliation. Cancel before dispatch abandons the pending intent; cancel after dispatch transitions to reconciliation and cannot undo a commit. Settled/cancelled intents cannot automatically replay. Intent phase helpers are guards, not persistence or an executable coordinator.

`cuisine`, `ingredient_like`, `ingredient_avoid`, `dietary_style` are the adopted supported preference types. Only explicit saves persist. Dietary style is a cooking preference, never verified allergy/health suitability. Recipe data keeps raw source measures, passage order/headings and reviewed annotations; no rating, serving, timing or nutrition fields are invented.

## Evolution and proof boundary

API version (`"2"`, consistently assistant/pair/health), shared schema (`2`), local command (`2`), database genesis (`2`), receipt (`1`) and catalogue identity are separate versions. Command2 accounts for the required edit guard; receipt1 and source catalogue identity remain unchanged. Data separately owns genesis2 and nondestructive rejection of incompatible v1 databases. Catalogue fingerprints come from Data's prepared artifact, not synthetic tests. Breaking field/enum/semantic changes require Brain coordination and regeneration, fixtures and adapter updates before consumers change. Strict older clients reject even newly added fields; optional additions are not transparently compatible. The generated manifest records the exact schema SHA-256 and compiler-free validator size/imports.

Fixtures use synthetic state and source-position ownership. Shared checks prove schema/runtime parity, frozen membership/equality/ordering, byte caps and canonical fingerprint behavior only. They cannot prove original retained source truth, cross-generation SQLite ownership, relevance/completeness, selection closure, actual removals/receipt provenance, transaction atomicity/CAS, immutable stored acknowledgements or provider interpretation. Data, AI and mobile must independently verify those boundaries, long-history/reopen/recovery behavior and real iPhone lifecycle/transactions before application acceptance.
